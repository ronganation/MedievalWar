# 1. Concise Verdict

The authoritative Contract Field Inventory contains **252 field-level validation rules** across all 21 approved contracts. This catalogue converts each rule into exactly one engine-agnostic validation entry, producing **252 validations** with explicit severity, validator ownership, trigger phase, required inputs, failure output, quarantine behavior, and deterministic ordering.

The catalogue does not create executable validators or claim implementation. It defines the minimum validation contract required before exact engine symbols, compilation, save conversion, or runtime testing can be accepted.

### Severity interpretation

- **Fatal:** Reject the affected definition, mutation, command, load, migration, mapping, transition, or persistence operation. Do not write invalid authoritative state.
- **Warning:** Preserve valid authoritative state, report the issue, and suppress unsafe derived output where necessary. A warning does not authorize guessing or ownership transfer.

# 3. Validator Ownership Review

## Trait Contract Validator

Owns validation of Trait definitions, Character Trait State, Trait commands, Trait queries, and Trait-bounded results. The validator may reject or report. The validator cannot write accepted Trait state; Trait Authority remains the sole writer.

## Reputation Contract Validator

Owns validation of Reputation definitions, Character-Audience Reputation State, Reputation source links, evaluation results, epithet commands, summaries, and influence results. The validator cannot create audience acceptance, evidence, memory, title, legitimacy, or authority.

## Canonical Identity Validator

Validates canonical person references and identity resolution boundaries. Migration Registries retain mapping authority, and Character Foundation retains represented person identity. The validator cannot invent or select an ambiguous identity.

## Information Boundary Validator

Validates observer, audience, access, visibility, and hidden-information boundaries. Character Network and Historical Memory retain substantive information ownership. Validation cannot create knowledge.

## Migration and Quarantine Validator

Validates source mappings, locked audit dispositions, chronology, ambiguity, quarantine, and idempotent migration behavior. It may place unresolved data in quarantine but cannot write an assumed destination.

## Save Compatibility Validator

Validates save, content, contract, migration, mapping, and deterministic-stream compatibility before owner state is loaded or converted. Unknown or unsupported versions fail safely.

## Deterministic Trace Validator

Validates reason completeness, visibility classification, source ordering, versions, tie breaks, and operation outcomes. Trace validation cannot expose hidden information or modify completed authoritative state.

## Sole-writer boundary

A validator is not an alternative state writer. Validators may:

- inspect authorized inputs;
- accept or reject an operation;
- emit diagnostics;
- request quarantine;
- emit deterministic reason traces;
- prevent persistence or consumption of unsafe data.

Validators may not:

- mutate Trait or Reputation state directly;
- reinterpret a locked audit classification;
- transfer ownership;
- create identity, audiences, evidence, memories, titles, offices, claims, authority, or strategic outcomes;
- invent IDs, registries, Gameplay Tags, or implementation symbols.

# 4. Trigger Phase Review

Validation executes at the narrowest phase capable of preventing invalid state:

1. **Definition import or revision:** immutable definition fields and content versions.
2. **New-campaign initialization:** Opening State fields before runtime construction.
3. **Command submission:** acquisition, transition, and epithet commands before owner mutation.
4. **Query or evaluation:** visibility, influence, summary, and Reputation evaluation before result consumption.
5. **Accepted runtime mutation:** authoritative state before persistence and event emission.
6. **Event-driven reevaluation:** source, access, contradiction, lifecycle, or state invalidation.
7. **Save write and load:** owner partitions and save-version compatibility.
8. **Migration extraction and mapping:** source provenance, mapping, destination readiness, and ambiguity.
9. **Quarantine review and resolution:** evidence-based resolution only.
10. **Trace emission:** completeness, ordering, versions, and visibility classification.

A rejected command or failed validation emits no authoritative state-change event.

# 5. Failure and Quarantine Review

## Failure output

Every failure output identifies:

- severity;
- evaluated contract;
- evaluated field;
- validation rule;
- authoritative owner;
- trigger phase;
- source or input references available to the validator;
- deterministic reason order;
- whether the operation was rejected, suppressed, preserved, or quarantined.

## Quarantine required

Quarantine is required when safe resolution is impossible because of:

- unknown or ambiguous identity;
- missing or conflicting source reference;
- unsupported audience;
- missing mapping or destination reference;
- duplicate or colliding legacy label;
- unmatched field;
- unsupported version;
- corrupt migration data;
- unresolved ownership dependency;
- chronology that cannot be reconciled safely.

## Quarantine not used as a repair mechanism

Quarantine preserves unresolved source data and prevents unsafe writes. Quarantine cannot:

- create a destination ID;
- choose among ambiguous people or concepts;
- fabricate an audience or source;
- reclassify an audited entry;
- copy evidence or narrative truth into Reputation;
- move Development, health, Archetype, Network, office, title, claim, or authority state into Trait.

# 6. Deterministic Validation Rules

1. Validate definitions before scenario or runtime records.
2. Validate canonical identity before specialist references.
3. Validate source existence and ownership before provenance links.
4. Validate information access before Trait visibility or Reputation audience evaluation.
5. Validate current state before command transitions.
6. Validate commands before state mutation.
7. Validate accepted state before emitting exactly one state-change event.
8. Validate owner partitions before save write.
9. Validate save versions before loading owner state.
10. Validate migration versions and mappings before destination construction.
11. Process quarantine dependencies before dependent records.
12. Sort by canonical subject where resolved, bounded audience where applicable, contract, field-rule order, source references, and stable ordering key.
13. Use versioned rules and stable numeric comparison/rounding.
14. Record tie-break reasons.
15. Do not use wall-clock time, frame timing, memory address, unordered-container iteration, asset discovery order, or UI order.
16. Equal state, inputs, content version, contract version, migration version, mapping version, and seed must produce equal diagnostics, quarantine decisions, traces, and accepted/rejected outcomes.
