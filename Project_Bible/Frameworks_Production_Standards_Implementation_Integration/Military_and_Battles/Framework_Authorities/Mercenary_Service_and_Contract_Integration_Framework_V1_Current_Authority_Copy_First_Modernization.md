## Part II — Current Owner-Routed Authority

## 1. Purpose and Scope

This framework defines a shared integration constitution for evaluating and coordinating finite service offered for consideration outside ordinary obligation recruitment. It keeps the concept strategically visible while routing identity, capacity, access, agreement, payment, command, supply, breach, closure, and records to their current owners.

It applies to a proposed service lifecycle only where the relevant owners admit the capability. It is not a mercenary roster, market, universal company schema, independent-actor simulation, or accepted production contract.

## 2. Authority Order and Currentness

Apply Project Bible 2.4, the latest applicable Design Expansion Checklist 3.7 update, Framework Architecture Map V2.2, the Military and Battles family index, and then the named substantive owner authorities in scope. The Checklist controls progress/closure/currentness, not runtime semantics. Owner silence and presence in the intended folder do not constitute adoption.

This document is subordinate to source owners. Where a controlling owner contract is unavailable, conflict remains unresolved and the dependent capability remains unpromoted.

## 3. Status, Evidence, and Non-Authorization

`StaticCheckedCopyFirstModernizationOwnerReviewRequired` means the document has been structured and cross-routed for static review. It is not owner acceptance, source completeness proof, canonical schema, Registry publication, payload approval, or implementation evidence.

No source has been modified. No project-native Unreal path, type, subsystem, data asset, save surface, importer, or runtime mercenary behavior was verified or changed by this document.

## 4. Modern Medieval II Design Promise

Mercenary service is an occasional, legible strategic option for a specific need, not a replacement for Realm military identity or ordinary finite recruitment. The player should be able to distinguish what is offered, who can authorize it, what is reserved, what must be delivered, what can block performance, and how the arrangement closes.

Keep routine administration bounded. Show material terms and decisive blockers; do not expose a universal loyalty meter, hidden reputation score, or exhaustive contract bureaucracy as a substitute for explanation.

## 5. Core Service Model

Treat service as a candidate relationship between a proposer, a service source, one or more authorized representatives, a beneficiary/employer, a defined scope, bounded terms, owner-approved capacity, and a lifecycle. The service framework records interfaces and case progression; it does not become the truth owner for any participant or resource.

The admitted shared concept is finite, person-bound, force-bound, agreement-bound, and owner-routed service. The existence of that concept does not verify a shared company, captain, broker, offer, agreement, or employer record schema.

## 6. Definitions and Terminology

Use “service candidate” for reviewable possibility; “offer” for a proposal; “agreement” for accepted terms; “reservation” for owner-held capacity; “assembly” for force formation; “readiness” for the military owner’s readiness result; and “service case” for the cross-owner integration envelope.

Do not use the legacy “mercenary” label to collapse allied contingents, household retainers, obligation forces, guild effects, religious service, rebels, prisoners, or event-driven forces into one class.

## 9. Service-Basis Classification

Keep separate at least: ordinary recruitment/obligation; regional or controller-access service; allied contingent; mercenary contract service; personal retinue/household attachment; religious or institutional service; coalition contribution; campaign-specific external service; rebel or outlaw force; prisoner/captive disposition; and emergent/event force.

Each case must name its proposed service basis and owner authority. Unclassified or overlapping cases are held for owner adjudication rather than silently mapped to a generic market.

## 10. Actor, Person, Force, and Company Distinctions

Canonical Persons are created and changed only by Character owners. A captain is a proposed role/reference, not a new Person. A company is not assumed to be a Character, Dynasty, Household, Unit, army, or autonomous faction. A force may contain multiple Units only through military owners and valid source capacity.

The shared sources do not establish a current universal captain/company/broker identity or succession schema. Such schema remains an explicit owner decision.

## 11. Contact, Broker, and Representation

Contact is an observed opportunity to communicate, not a broker appointment. Broker is a representation/agency role that requires an identified Person or institution, mandate, scope, duration, disclosure rules, and revocation owner. Captain is not automatically broker, principal, owner, employer, commander, or agreement party.

Route contact and communication context through Character Network and Information/Intelligence. Route mandate, representation, and agreement authority through Diplomacy/Law owners. Without valid mandate evidence, the representation-dependent transition is blocked.

## 12. Service Lifecycle State Model

Use a proposed, owner-reviewed state sequence:

```text
Unassessed
-> CandidateAdmitted
-> ContactPossible
-> RepresentationVerified
-> OfferDrafted
-> OfferDelivered
-> Negotiating
-> Offered
-> AcceptedPendingOwnerChecks
-> CapacityAndAuthorityReserved
-> AgreementEffective
-> MusterRequested
-> Assembling
-> ReadinessReview
-> InService
-> SuspendedOrDisputed (when supported)
-> CloseoutPending
-> ReleasedOrTerminated
-> DemobilizedOrReturned (owner-specific)
-> ArchiveReferences
```

This is a design lifecycle, not an implemented enum. Transitions require typed owner receipts; invalid, stale, conflicting, or missing receipts block advancement.

| Transition boundary | Required evidence/owner result | Failure handling |
|---|---|---|
| Unassessed -> CandidateAdmitted | Named source, basis, identity references, authority route, eligibility evidence | Hold as unknown or reject with reason; do not synthesize a source |
| CandidateAdmitted -> ContactPossible | Contact/communication opportunity from relevant owners | Remain candidate; no inferred contact |
| ContactPossible -> RepresentationVerified | Identified representative and valid, scoped mandate | Block offer delivery; preserve mandate uncertainty |
| OfferDrafted -> OfferDelivered | Complete proposal and delivery/visibility receipt | Keep draft or mark delivery failure; no presumed receipt |
| Negotiating -> Offered | Explicit current proposal version and valid terms | Supersede prior terms; no implicit acceptance |
| Offered -> AcceptedPendingOwnerChecks | Explicit authorized acceptance for exact offer version | Reject stale/unauthorized acceptance |
| PendingOwnerChecks -> CapacityAndAuthorityReserved | All required owner prepare/commit receipts | Abort/compensate partial reservations; never show success |
| Reserved -> AgreementEffective | Agreement and legal/diplomatic owner confirmation | Keep reserved only according to owner expiry; else release via receipt |
| AgreementEffective -> MusterRequested | Valid scope, term, capacity, and assignment request | Block request if a prerequisite is absent |
| Assembling -> ReadinessReview | Military, logistics, access, and command receipts | Remain unready; show owner-provided blocker |
| ReadinessReview -> InService | Military readiness and service-start confirmation | No inference from arrival or payment |
| InService -> CloseoutPending | Expiry, termination, withdrawal, completion, or dispute trigger | Keep unresolved owners/cases open |
| CloseoutPending -> ReleasedOrTerminated | Agreement/mandate/assignment closure receipts | Preserve unresolved obligation and reservation state |
| ReleasedOrTerminated -> DemobilizedOrReturned | Separate force, custody, return, and persistence receipts | Do not assume safe return or reintegration |

The table is a validation aid, not a specification of a universal state machine. An owner may reject a transition, define narrower states, or require further states within its domain. Retrying a request must be idempotent and tied to the same request identity/version.

## 13. Candidate Admission and Eligibility

Candidate eligibility is a conjunction of separately owned conditions: a valid source reference, authorized representation, a plausible service basis, source-owner permission, finite available capacity, feasible terms, compatible route/access, and no unresolved blocking prohibition.

Eligibility does not mean offer, consent, capacity, agreement, reservation, assembly, readiness, or service. Unknown remains distinct from false or zero.

## 14. Offer and Negotiation

An offer is a revocable, expiring proposal with identified parties/mandates, service scope, proposed duration/window, requested capacity references, expected duties, consideration references, command/access conditions, limits, risk disclosures, and a validity context. Exact term fields and obligations require owner review.

Counteroffer, refusal, delay, withdrawal, expiry, and supersession are explicit outcomes. Silence is not acceptance. An unaccepted offer reserves no capacity and mutates no owner.

## 15. Agreement and Contract Terms

Agreement validity belongs to diplomatic, legal, and economic owners in their respective scopes. This framework requires cross-references to those determinations; it does not declare a contract legally valid.

Terms must not imply automatic ownership of People, Units, equipment, captured property, routes, or markets. Amendments, suspension, replacement, termination, and continuity require the relevant owner’s transaction and receipts.

## 16. Capacity, Pool, and Source Reservations

All capacity is finite, typed, source-owned, geographically/institutionally scoped where applicable, and shared across consumers. Query/reconcile the Military Recruitment Pool owner and relevant specialist source owner. Reject double reservation and source duplication.

No pool values, replenishment rates, availability quantities, company sizes, or source instances are created here. The old source’s numeric pool examples are quarantined provenance, not admitted data.

## 17. Reservation, Assignment, and Atomicity

Reservation is an owner-held claim on eligible source capacity; assignment/activation is a separate military operation. Reservation does not create or activate people, units, animals, equipment, readiness, payment, or agreement performance.

Prepare/commit/abort/retry and idempotence must be owned by the relevant transaction authority. Multi-owner partial success must not be represented as success. A failed commit releases only reservations for which the owner returns release receipts.

## 18. Assembly, Arrival, and Readiness

Muster/assembly, transit/arrival, and readiness are independent owner determinations. Contract acceptance cannot instant-create an assembled or ready force. Arrival is not proof of equipment, supply, command integration, cohesion, or mission readiness.

Military Assignment, Roster, Logistics, Command, and relevant access owners return scoped receipts; absent or contradictory receipts block service readiness.

## 19. Service Scope and Mission Limits

Service scope is explicit and bounded by authorized purpose, geography, duration/window, force references, command relationship, access rights, prohibited actions, and termination/withdrawal conditions. Mission expansion requires valid amendment and affected-owner consent.

The authority does not define concrete mission catalogues, regional campaign plans, route capacity, or strategic objectives.

## 20. Employer, Owner, and Commander Separation

Employer/beneficiary is a contractual role only. It is not automatically the force owner, Unit owner, source authority, commander, sovereign, equipment owner, or person’s legal status. Command must be authorized and communicated through Command/Control owners.

Conflicts between service terms, source command, host command, and lawful authority are held for explicit owner adjudication; no universal command precedence is invented here.

## 21. Payment, Price, and Fiscal Flow

This framework defines no price, fee, wage, upkeep, discount, arrears threshold, bonus, market, or payment schedule. Terms reference Treasury/Markets/Fiscal Flow transactions. An agreement is not payment; a reservation is not payment; payment authorization is not delivery; a fiscal receipt is not loyalty or command.

Keep debt, credit, ransom, compensation, gift, fine, repayment, and ordinary wages in their respective fiscal records. Market does not own Treasury; Treasury does not create revenue. Refusals and external locks remain authoritative.

## 22. Consideration, Property, Loot, and Material Delivery

Equipment, property, goods, loot, access, use rights, and material deliveries require their respective ownership/permission, logistics, fiscal, and law receipts. A promise or contract term cannot create material stock or transfer title automatically.

Loot permission is not delivery or lawful ownership. Captured property and ransom are not generic mercenary rewards; route to lawful and fiscal owners. Unreconciled seizure is not booked as revenue.

## 23. Supply, Transport, Routes, and Access

Route is not market access, navigability, transport capacity, safe conduct, or delivered supply. Trade access does not establish mercenary availability. Supply and physical transport owners determine stock, movement, delivery, consumption, and recovery.

This authority cannot create routes, ports, ships, crews, transport, depots, supply stock, or movement permission. Every service feasibility claim cites owner-provided receipts.

## 24. Command, Orders, and Communications

Command authority is separately owned, scoped, and evidenced. Orders are transmitted intent, not instant control. Force-level coordination must respect valid channels, communication opportunity, delay, and acknowledgement.

Mercenary service terms do not transfer command by implication. Conflicting orders, invalid authority, unavailable communication, or scope violations are explicit command blockers.

## 25. Performance, Acceptance, and Closeout

Performance evidence is task/term specific and owner supplied. Acceptance, partial performance, nonperformance, cure, dispute, and remaining obligations require auditable receipts. Closeout reconciles physical return, capacity release, fiscal state, casualties/persistence, custody/property, access, and unresolved claims with respective owners.

Closing a contract does not delete surviving forces, Persons, veterans, records, obligations, or evidence.

## 26. Refusal, Withdrawal, and Expiry

Refusal, withdrawal, expiry, and nonrenewal are valid distinct outcomes. Refusal is not automatically breach. Expiry does not imply acceptance or extension. A party’s authority to withdraw is a term/law/diplomacy determination.

Any consequence requires an applicable agreement and owner determination. There is no automatic retaliation, desertion, rebellion, or transfer.

## 27. Breach Allegation, Evidence, and Remedy

An alleged breach is not a proven breach. Record the allegation, cited term, evidence provenance/visibility, response, dispute status, owner determination, available cure/remedy, and final disposition separately.

Diplomacy owns agreement/performance/breach/settlement processes; Law owns jurisdiction/liability/evidence/remedy/enforcement where applicable; Public Order integration routes grievances and remedies but does not execute suppression or restoration. The mercenary authority does not judge guilt or impose remedy.

## 28. Arrears, Grievance, and Noncompliance

Arrears are fiscal state, not a loyalty or desertion flag. Grievance is a typed case, not proof. Noncompliance, inability, refusal, breach, and coercion remain distinguishable.

Route fiscal reconciliation to Treasury/Fiscal Flow, law and obligations to Law and Policy, public response/remedy to Public Order integration, and force consequences to Military/Diplomacy owners. No automatic desertion, defection, rebellion, or payment is permitted.

## 29. Loyalty, Reliability, Reputation, and Memory

Do not introduce a universal mutable loyalty or reliability score. Payment, service history, reputation, evidence, testimony, communication, and belief remain typed, sourced, scoped, actor-visible, and owned by their respective systems.

Reputation is not reliability. Historical Memory owns records, evidence references, narrative/reception and legacy—not current force truth, identity, command, or universal reputation. A recorded allegation is not a canonical fact.

## 30. Desertion, Defection, Rebellion, and Displacement

Desertion, defection, rebellion, surrender, withdrawal, and displacement are different events and outcomes. No one is inferred solely from arrears, defeat, supply stress, culture, religion, or lost command.

If a qualified owner later authorizes these outcomes, it must issue the event/transition receipt and consequences. This file defines no probability, trigger threshold, destination, enemy transfer, or spawned host.

## 31. Death, Capture, Incapacity, and Representation Failure

Death, capture, incapacity, disappearance, withdrawal, or invalid mandate of a captain/broker/representative are Character/Law/Diplomacy events. They do not delete a company or agreement automatically and do not transfer command or succession automatically.

Continuity, replacement, substitute authority, or termination require explicit terms and owner approval. No shared captain/company succession schema is established here.

## 32. Dismissal, Demobilization, Release, Return, Reintegration

Dismissal ends a service relationship only if the relevant owner confirms it. Demobilization is a separate force lifecycle outcome. Release is not safe return; return is not reintegration; return does not restore capacity or personal relationships automatically.

Military Closure/Veteran Persistence, Character, Law, Diplomacy, Population, Logistics, and custody owners determine their own transitions and receipts.

## 33. Captives, Prisoners, and Recovered Persons

Captivity and release are law, diplomacy, custody, and Character lifecycle concerns. A captive is not automatically a recruit, mercenary, replacement, or source capacity. Consent and legal eligibility are not inferred from capture.

Recovered people require identity, custody, lawful disposition, safety, and owner-controlled reintegration. No captive-to-mercenary pipeline is authorized.

## 34. Animals, Equipment, and Casualty Recovery

Animal and equipment state remain separate typed resources. Rider casualty is not mount casualty; recovery is not ownership; salvage/capture is not readiness; recovered animals do not automatically become remounts.

Use Military Animal Custody/Recovery and Equipment owners. This framework creates no horses, weapons, vessels, equipment, casualty state, recovery counts, or replacement capacity.

## 35. Regional, Cultural, Religious, Guild, and Institutional Interfaces

Regional access, culture, religion, guild sponsorship, and institutional context may be inputs only through the respective owners. They do not establish a generic unlock, source capacity, consent, loyalty, authority, or service.

Legacy category/example lists are provenance. No current regional roster, named company, guild effect, religious authorization, access rule, or package is created here. Southern Norman facts remain confined to their own review candidate.

## 36. Historical and Era Compatibility

Historical date, Era labels, culture, technology, and historical memory inform owner-controlled content review; none forces availability or historical outcomes. Preserve the three-track time constitution: Historical +21 months per turn; Biological +7 months per turn; Campaign Season advances one ordered Winter/Spring/Summer/Autumn step each turn.

Legacy Early/High/Late examples are not admitted time gates, roster entries, or current content.

## 37. Markets, Trade, and Availability

Markets own exchange/settlement and price/availability observations; economic owners own material/fiscal conservation. A route is not a market; a market is not an available company; wealth does not create military capacity; trade traffic does not create consent or service.

No mercenary market, trade-center attraction, price fluctuation rule, discount, supply, or availability record is created.

## 38. Government, Law, and Political Context

Government preference or law may shape lawful capacity, duty, authorization, or review only through its owner. Government labels do not imply “limited/heavy” reliance. Taxation and military obligations remain Law/Policy and fiscal concerns.

No Government type, law, coercive authority, service obligation, political penalty, or automatic consequence is created.

## 39. Public Order, Grievances, and Recovery

Owner-provided hardship, property loss, coercion, arrears, or alleged misconduct may be routed as evidence or grievance to Public Order integration. The integration owns case-envelope and remedy routing semantics, not public-order truth or remedy execution.

Public Order activation, suppression, restoration, compensation, property recovery, and material recovery remain unimplemented here.

## 40. Player Information, Privacy, and Explanation

Presentation is visibility-filtered. Distinguish public offer/term facts, authorized private negotiations, holder-specific knowledge, evidence provenance, unknown/hidden/stale/conflicting state, and external-private information.

Do not expose undisclosed bids, private intent, negotiations, grievance, employer/company evidence, or another actor’s knowledge unless Information/Intelligence and relevant owners authorize it. UI is not a state owner and cannot convert inference to fact.

## 41. AI Evaluation and Proposal Boundaries

AI reads only actor-visible owner state, assesses feasibility and alternatives, can abstain, explains blockers and uncertainty, and submits owner-routed requests. Owners validate and execute.

Potential considerations may include urgency, available owner-certified capacity, fiscal ability, supply/route feasibility, legal authority, command, and service risk. No weights, scores, free capacity, payment, contract, or force are invented. Player and AI use the same constraints and receipts.

## 42. Player Workload and Interaction Budget

Present a small number of meaningful choices: compare accepted alternatives, inspect decisive terms/blockers, negotiate or refuse, authorize a valid transaction, and resolve consequential exceptions. Routine validation and receipts remain automatic/inspectable.

Do not require routine micromanagement of loyalty, hidden timers, arbitrary contract sliders, or unbounded event handling. No interface is implemented by this authority.

## 45. Persistence, Save/Load, and Migration

Persist only owner-approved authoritative state and necessary transaction/evidence references. Do not serialize derived availability, actor-hidden knowledge globally, transient evaluation, UI, or duplicate owner truth as authoritative data.

Save/load schema, migration, direct alias mapping, ambiguity quarantine, replay, rollback, idempotence, and advanced-save protection require separate owner-approved contracts and validation. This file does not alter save format or migrate data.

Persistence candidates, subject to each owner's approval:

- stable service-case and agreement references;
- owner receipts and transaction/evidence references required to reconstruct the accepted lifecycle;
- unresolved dispute, obligation, reservation, or closeout references owned by the responsible systems;
- schema/content/owner versions and provenance sufficient to reject incompatible replay.

Do not persist as authoritative truth:

- calculated market availability or a copied recruitment pool;
- a derived “loyalty/reliability” total;
- private intent or globalized knowledge;
- a rendered UI/read model or AI score;
- an unverified offer, rumor, or allegation as proven fact;
- a second copy of a Character, Unit, Treasury, market, route, supply, command, or legal owner record.

Any future migration must be direct, versioned, deterministic, idempotent, reversible or explicitly compensating, and ambiguity-quarantining. An unknown source identifier, missing owner receipt, duplicate case, conflicting term version, or external-private datum must not be guessed into a live service state. Advanced saves must remain unchanged unless a separately approved migration explicitly transforms them.

## 47. Validation Rules and Failure Classification

Fatal design violations include duplicated owner state; invented capacity or values; offer treated as agreement; agreement treated as reservation/performance; employer treated as owner/commander; payment treated as loyalty; arrears treated as desertion; allegation treated as breach; refusal treated as breach; regional route generalized; person/force/animal/equipment collapsed; private state exposed; legacy example promoted; or static review described as runtime validation.

Warnings include incomplete provenance, unresolved owner authority, ambiguous role/mandate, stale or contradictory receipt, unapproved terms, weak explanation, overbroad player workload, or unknown persistence interface. Fatal results block promotion; warnings require disposition.

Validation should distinguish at least these classes:

| Class | Meaning | Required response |
|---|---|---|
| Structural | Missing, extra, malformed, or mis-typed envelope field | Reject the request/receipt; report exact field |
| Identity | Unknown, aliased ambiguously, retired, or conflicting owner reference | Quarantine; require Registry/identity-owner decision |
| Authority | Missing, expired, scoped incorrectly, or disputed mandate | Block dependent transition |
| Capacity | Missing, stale, duplicate, or contested reservation/capacity receipt | Block; request owner reconciliation |
| Terms | Offer/agreement version mismatch or invalid term reference | Reject stale operation; preserve both versions |
| Visibility | Data supplied to an unauthorized holder or exposed in presentation | Security/privacy failure; stop release and refer to Information owner |

| Transaction | Partial commit, duplicate effect, or missing rollback link | Fail closed and reconcile with coordinator |
| Evidence | Unsupported, inaccessible, or provenance-free assertion | Downgrade to unknown/unverified; no canonical determination |
| Determinism | Equivalent inputs normalize differently | Block promotion and preserve replay evidence |
| Persistence | Owner state duplicated, missing, or silently defaulted on load | Fail load/migration safely; quarantine affected record |

Static validation can establish only structural properties of the inspected document or future fixture. It cannot certify legal validity, historical truth, balance, runtime correctness, or owner approval.
