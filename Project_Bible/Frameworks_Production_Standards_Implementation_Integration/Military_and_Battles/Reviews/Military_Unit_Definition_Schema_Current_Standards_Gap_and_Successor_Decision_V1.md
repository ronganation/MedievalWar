# Military Unit Definition Schema Current-Standards Gap and Successor Decision V1

## 1. Decision

**Recommendation: split future contracts into separate Master Profile, qualitative handoff, Unit Definition, and Game Card schemas.**

Do not edit either V1 JSON file in place in this audit. Preserve [Unit_Definition_Schema_V1.json](../Implementation_Integration/Schemas/Unit_Definition_Schema_V1.json) and [Unit_Definition_Validation_Rules_V1.json](../Implementation_Integration/Schemas/Unit_Definition_Validation_Rules_V1.json) as the historical narrow V1 contract/rules pair until the responsible owner authorizes future contract work. This is a design recommendation only; it does not authorize schema creation, production import, Registry changes, Opening State changes, or implementation.

The current stack explicitly gives distinct jobs to the durable Master Unit Profile, qualitative implementation handoff, static Unit Definition, and derivative Game-Facing Unit Card. V1 requires one object containing `identity`, `role`, `equipment`, `recruitment`, `lineage`, `AI_guidance`, `presentation`, `historical_basis`, and `implementation`; that conflates authoring completeness, qualitative semantics, static definition, UI presentation, and implementation evidence. The current standards supply better ownership boundaries than one expanded monolithic schema.

The implementation target remains Unreal Engine **5.8**. No compile or runtime validation is claimed. Temporal tracks remain independent: Historical progression is 21 months per strategic turn; Biological progression is 7 months per strategic turn; Campaign Season is one ordered Winter, Spring, Summer, Autumn step per strategic turn.

## 4. V1 validation-rules assessment

The paired rules are explicitly static-only and say they do not prove Registry allocation, Opening State inclusion, active-unit existence, importer success, compilation, runtime behavior, save/load, migration, replay, performance, tactical balance, or battle validation. That boundary remains correct and must be preserved.

The rules also preserve important constraints: no active state in a definition (`UDV-004`); recruitment-source separation (`UDV-008`); formation eligibility rather than runtime formation (`UDV-010`); explicit source/historical classification (`UDV-016`); selective inheritance evidence (`UDV-017`); transparent AI blockers (`UDV-018`); legacy-content preservation (`UDV-021`); direct duplicate comparison (`UDV-022`); and an implementation gate (`UDV-024`). These are retained concepts, not deletion candidates.

The present standards require future validators to distinguish authoring maturity from validation state, to retain evidence hashes and scope, and to keep separate contracts for static definition, Opening State, runtime, saves, migrations, and presentation. The V1 `status` enum and V1 rule set do not encode that full lifecycle.

## 5. Successor split decision

Create separate future contract proposals, only after an explicit authorization:

1. **Master Profile schema** — complete substantive unit-family authoring, provenance, owner, uncertainty, feature coverage, and maturity.
2. **Qualitative handoff schema** — semantic vocabulary keys, Faction Military Expression, Unit Specialization, formation/capability references, qualitative readiness, evidence receipts, and blockers without premature numeric or runtime claims.
3. **Unit Definition schema** — static implementation-bound definition, resolved/candidate identity, source/pool/availability references, eligibility, and explicit non-ownership of Opening State/runtime state.
4. **Game Card schema** — derivative player-facing content/art/stat presentation with versioned derivation from a Master Profile; never the substantive authority.

Keep save/migration and runtime contracts separately owned rather than making them additional fields that imply implementation. Keep V1 and its validation rules byte-preserved as historical V1 evidence until an owner-authorized successor and disposition exist.
