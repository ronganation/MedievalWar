## 1. Purpose

The Frameworks and Integration Authorities repository contains reusable constitutional design, bounded specialist ownership, cross-owner integration contracts, static-design closure evidence, implementation handoffs, and retained predecessor material.

Frameworks define reusable ownership, rules, lifecycles, interfaces, and authoring constraints. Integration authorities define how separate owners exchange typed evidence, observations, proposals, requests, receipts, traces, and validation results without transferring private state or creating unauthorized mutation.

A progress update records workstream truth and anti-repetition boundaries. A progress update does not become the substantive framework, replace the stable Design Expansion Checklist, or prove implementation.

```text
Framework != System Implementation
Integration != Ownership Transfer
Progress Update != Substantive Authority
Static Closure != Runtime Implementation
Current Authority != Canonical Registry Publication
Owner Review Required != Owner Approval Assumed
```

## 2. Core Framework Doctrine

Every framework and integration authority must preserve:

- Medieval II as the campaign spine;
- the campaign map as the primary strategic workspace;
- armies, settlements, Provinces, diplomacy, succession, institutions, population, logistics, and territory as visible strategic realities;
- deep internal simulation with selective player exposure;
- typed owner boundaries and owner-controlled mutation;
- actor-visible knowledge, uncertainty, contradiction, staleness, and abstention;
- deterministic processing and explicit ordering;
- stable canonical IDs and direct one-step migration;
- definitions, Opening State data, runtime state, transient evaluation, presentation, save, migration, and evidence as separate layers;
- proposal-only AI and owner-routed transactions;
- atomic commit, rollback, replay, and advanced-save protection;
- finite people, equipment, horses, officers, money, goods, transport, route, and supply capacity;
- Unknown as distinct from zero, empty, neutral, false, absent, unsupported, and malformed;
- validation claims no broader than retained evidence;
- limited routine player workload and explanation centered on strategic decisions.

## 12. Status Vocabulary

- Design: proposed direction without completed static inspection.
- StaticChecked: design, data, or source inspected only in the recorded scope.
- FoundationComplete: required design foundations exist for the stated scope.
- CompileValidated: compilation succeeded with retained evidence.
- RuntimeValidated: execution succeeded with retained evidence.
- ImporterValidated: parsing, validation, translation, routing, transactions, and receipts were demonstrated.
- SaveLoadValidated: authoritative state was written and restored.
- MigrationValidated: direct migration executed against representative artifacts.
- ReplayValidated: equivalent authoritative inputs reproduced equivalent results within the stated boundary.
- RealmFrozen: Realm foundation is stable at its recorded boundary.
- Partial: substantial work exists and named gaps remain.
- Planned: accepted future work.
- Deferred: intentionally postponed.
- Quarantine: authoritative use is blocked pending resolution.
- Legacy: useful intent remains while ownership is superseded.
- Superseded: a newer authority controls the subject.
- Rejected: prohibited as authority or implementation source.

Qualifiers and review states are not substitutes for evidence status.

## 13. Framework Creation and Reopening Gate

Create a new shared framework only when all are true:

- the capability recurs across multiple Realms or systems;
- current ownership is missing, ambiguous, or materially conflicting;
- strategic outputs and interfaces are clear;
- AI or implementation requires a reusable contract;
- save, migration, replay, or rollback risk exists without shared standardization;
- no current framework or integration authority can own the capability cleanly;
- the proposal avoids duplicate mutable state and universal-owner creep;
- the proposal has dependencies, acceptance criteria, evidence requirements, rollback, and owner gates.

A closed family reopens only for:

- new substantive evidence;
- corrected controlling dependency;
- owner decision changing scope;
- proven cross-owner contract defect;
- verified live-project architecture evidence;
- compile, runtime, save, migration, replay, rollback, or performance failure;
- a new Realm, Theater, or capability that cannot be represented by the current authority family.

Filename symmetry, equal file counts, cosmetic currentness, documentation volume, or another family's version number are not valid reopening reasons.
