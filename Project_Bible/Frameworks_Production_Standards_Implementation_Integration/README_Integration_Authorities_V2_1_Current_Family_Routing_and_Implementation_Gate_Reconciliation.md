## 2. Purpose

This repository surface contains cross-domain integration authorities, reconciliation reviews, current-authority audits, validation records, migration guidance, owner-decision records, implementation handoffs, and bounded progress updates for Medieval War.

Integration authorities define how separately owned systems exchange typed evidence, observations, knowledge references, proposals, feasibility requests, responses, command requests, owner receipts, findings, traces, hashes, and validation results. Integration does not collapse ownership, manufacture capacity, bypass consent, or directly mutate authoritative Campaign state.

```text
Integration != Ownership
Reference != Authority Transfer
Observation != Fact Creation
Proposal != Execution
Receipt != Performance Unless Issued By The Performance Owner
Static Closure != Runtime Implementation
Documentation Promotion != Runtime Activation
```

This operating guide does not replace Project Bible 2.4, Design Expansion Checklist 3.7, README Frameworks V5.1, Framework Architecture Map V2.1, Foundation or Specialist Frameworks, Realm authorities, Opening States, Registries, implementation contracts, source manifests, closure reviews, owner decisions, or retained evidence.

## 4. Non-Negotiable Integration Rules

- Every authoritative concept and mutable state has a named owner.
- Reading, displaying, summarizing, comparing, referencing, or hashing owned state does not transfer ownership.
- Definition, Opening State fact, mutable runtime state, transient evaluation, presentation, save, migration, and evidence remain separate.
- Integration evaluators may read, normalize, validate, compare, hash, trace, explain, and propose owner-routed requests.
- Integration evaluators do not directly mutate authoritative Campaign state.
- AI reads actor-visible state, evaluates alternatives, explains reasons, abstains where appropriate, and proposes requests. Owners validate and execute.
- No universal strategic, legitimacy, relationship, standing, value, loyalty, power, threat, or utility score may replace separately owned typed state.
- Unknown is not zero, neutral, safe, false, absent, available, or compliant.
- Pressure is not outcome. Proposal is not consent. Consent is not capacity. Claim is not ownership. Recognition is not legitimacy. Authority is not performance.
- Stable canonical IDs, explicit provenance, deterministic ordering, transaction boundaries, idempotence, rollback, save safety, migration safety, and advanced-save protection are required.
- Opening State data initializes an uninitialized new Campaign at most once and must not overwrite advanced state.
- External private state is never authored locally. Reciprocal state requires owner-versioned requests and receipts.
- Integration cannot create people, units, pools, equipment, horses, officers, money, goods, ships, ports, routes, access, supply, knowledge, consent, performance, relationships, alliances, wars, peace, Titles, Claims, Offices, or institutions.

## 8. Ownership, External Locks, and Mutation Boundary

During evaluation, planning, conformance review, and read-only discovery, integration authorities authorize zero direct authoritative mutations.

Permitted operations:

- read owner-provided snapshots;
- inventory typed evidence and provenance;
- normalize records deterministically;
- validate IDs, fields, versions, ownership, ordering, and boundaries;
- compare bounded alternatives;
- create findings, explanations, and review candidates;
- hash source artifacts, normalized contracts, and traces with separate hash roles;
- submit owner-routed requests;
- stage transactions without committing owner state.

Prohibited direct operations include:

- creating or modifying Characters, Dynasties, Households, relationships, Offices, Titles, Claims, institutions, Facts, or Memory;
- moving armies or fleets;
- creating Units, recruitment pools, equipment, horses, officers, ships, routes, ports, access, supply, or transport;
- spending treasury or creating goods, tribute, ransom, compensation, loans, or delivery;
- creating, accepting, performing, suspending, or terminating agreements for another owner;
- declaring war, peace, truce, recognition, legitimacy, submission, protection, or annexation;
- changing property, settlement control, occupation, administration, or Realm ownership;
- activating Objectives, Designations, Rewards, Victory, Momentum, Emergence, or Character admission;
- rebasing, reconstructing, or overwriting advanced saves.

Authoritative change occurs only through the owning system's validated transaction path.

## 9. Status and Validation Language

Use statuses literally and always bound them to the exact scope:

- Design: proposed direction without completed static inspection.
- StaticChecked: inspected document, data, or source structure only.
- FoundationComplete: required design foundations exist for the stated scope.
- CompileValidated: compilation succeeded with retained evidence.
- RuntimeValidated: execution succeeded with retained evidence.
- ImporterValidated: parsing, validation, translation, owner routing, transaction, and receipt behavior were demonstrated.
- SaveLoadValidated: authoritative state was written and restored.
- MigrationValidated: versioned direct migration executed against representative artifacts.
- ReplayValidated: equivalent authoritative inputs produced equivalent results within the stated boundary.
- RollbackValidated: an approved rollback was executed and verified.
- Quarantine: authoritative use is prevented pending resolution.
- Superseded: retained for provenance or migration but no longer controlling.
- Rejected: prohibited as authority or implementation source.

ReviewOnly, Candidate, Draft, StaticChecked, FoundationComplete, and OwnerReviewRequired do not mean Active, production-ready, compile-validated, runtime-validated, or owner-approved.

## 10. Copy-First Authoring Standard

Every new or revised integration authority must:

- locate and read the complete immediate substantive source;
- preserve all compatible substantive content;
- preserve source identity, version lineage, owner boundaries, player-facing content, AI content, uncertainty, validation, migration, and rollback material;
- integrate improvements within the authority rather than replacing it with a short summary;
- compare source and successor section by section;
- record every substantive removal, relocation, consolidation, or rejection;
- distinguish repository-verified, session-verified, candidate, unknown, quarantined, and implementation-evidenced dependencies;
- distinguish current authority from predecessor provenance;
- use Unreal Engine 5.8 as the implementation target while reporting unperformed validations honestly;
- preserve the three-track temporal constitution and January 1, 1062 opening boundary;
- avoid Registry, schema, save-format, payload, runtime, or Unreal mutation unless separately authorized;
- perform literal completeness, formatting, ownership, activation, and validation scans before delivery.

## 14. Determinism, Ordering, and Hashing

Equivalent authoritative inputs must normalize equivalently. Every record family requires explicit comparators and stable ordering.

Do not include these values in normalized authoritative hashes:

- memory or pointer addresses;
- filesystem order;
- unordered map iteration;
- localized text;
- wall-clock time;
- transient UI state;
- machine-specific paths;
- nonauthoritative progress-update timestamps unless the contract explicitly owns them.

Keep hash roles separate:

```text
Exact-Byte Artifact Hash -> Source Integrity
Normalized Contract Hash -> Semantic Normalization
Transaction Input Hash -> Prepared Mutation Intent
Campaign State Hash -> Authoritative Runtime State
Evidence Package Hash -> Retained Validation Bundle
```

## 15. Save, Migration, Replay, and Advanced-State Safety

Persist only owner-approved authoritative runtime state. Do not persist recomputable utility totals, temporary candidate arrays, pointer references, unsorted transient maps, hidden reasoning, localized explanation text, or Opening State defaults as current state.

Migration must preserve:

- direct one-step ID redirects;
- source and target versions;
- owner and namespace changes;
- decomposition of deprecated universal scores;
- typed Objective, pressure, finding, proposal, command, agreement, confidence, and lifecycle evolution;
- ambiguity quarantine;
- advanced-state divergence;
- no replay from a current Opening State;
- idempotent repeat handling and conflicting-payload rejection.

Alias chains fail. Ambiguous identities quarantine. Deprecated IDs are prohibited in new authoritative state. Static definitions cannot reconstruct advanced runtime history.

## 17. Progress Update Disposition

Checklist progress updates record milestones, currentness, supersession, nonmutation receipts, owner gates, and anti-churn stopping points. They are useful inputs to repository currentness and future-session recovery.

They do not:

- replace substantive frameworks or integration authorities;
- become competing current-authority indexes;
- create Registry, Opening State, runtime, or Unreal authority;
- prove compile, runtime, importer, save, migration, replay, rollback, or performance behavior;
- authorize repeating a closed audit without a valid reopening trigger.

Where one progress update explicitly supersedes a bounded status in an earlier update, the later update controls only that bounded subject. The earlier update remains evidence for all other completed work it records.
