**Status:** Draft Contract / Static-Check Candidate

**Target:** Unreal Engine 5  
**Owner:** Character Network  
**Realm Scope:** Denmark  
**Opening Baseline:** January 1062  
**Prototype Turn Length:** Seven months  
**Authority Class:** Realm Network Integration Contract  

---

## 1. Concise Verdict

Denmark Network V1 is approved for bounded integration planning based on its completed dry preflight result:

- 20 directed relationship directions;
- zero authoritative mutations;
- four unresolved external locks;
- no Compile-Validated claim;
- no Runtime-Validated claim.

The correct classification is **Validate, Integrate, then Implement**.

This contract does not redesign Denmark. It does not expand the active roster, invent relationship values, resolve external authorities by assumption, or authorize runtime mutation. It defines how the already preflighted Denmark Network content connects to Character Foundation, Opening State, dynasty, title, office, claim, household, institutional, historical, and AI owners.

---

## 2. Purpose

This contract establishes the integration boundary required to move Denmark Network V1 from a dry, static network package toward a typed UE5 implementation.

It ensures that:

- each network direction remains directed and independently meaningful;
- canonical identities resolve before edge construction;
- the network does not absorb title, office, dynasty, household, claim, institution, or historical truth;
- Opening State initializes Denmark once for a new campaign;
- advanced saves are not overwritten;
- unresolved external locks remain explicit and non-mutating;
- equal inputs produce equal normalized outputs;
- AI reads network state and proposes commands, while owners validate and execute.

## 7. Directed Edge Contract

Each integrated network direction requires a typed record equivalent in responsibility to:

```text
EdgeId
NetworkId
SourceNodeId
TargetNodeId
RelationshipContextId
RelationshipTypeId
OpeningStateReference
VisibilityState
LifecycleState
SourceProvenance
ContentVersion
ValidationState
```

Mutable dimensions may be added only when authorized by the Character Network contract and the Denmark content authority.

### 7.1 Directionality

For every edge:

```text
Source -> Target
```

is independently authored and validated.

The existence of:

```text
A -> B
```

does not create:

```text
B -> A
```

A reverse direction requires its own authority, source provenance, edge identity, initialization, and validation result.

### 7.2 Endpoint types

Permitted endpoint kinds may include:

- canonical person;
- dynasty;
- office;
- institution;
- household;
- title;
- power center;
- region;
- external actor;
- legacy reference where no living agency is implied.

Each endpoint must identify its entity kind. Person, office, title, dynasty, institution, household, region, and realm IDs must not be interchangeable.

### 7.3 Context requirement

An edge must carry or resolve a typed context when the relationship depends on:

- succession;
- claim;
- office service;
- command;
- household access;
- guardianship or protection;
- alliance or coalition;
- institutional cooperation;
- regional authority;
- reward or obligation;
- evidence or memory.

A generic personal edge cannot replace the underlying arrangement.

---

## 8. Canonical Identity Resolution

Integration resolves endpoints in this order:

1. validate a current canonical ID;
2. apply one direct versioned migration mapping;
3. reject deprecated IDs from normalized output;
4. reject alias chains;
5. quarantine unknown or ambiguous IDs;
6. preserve cross-realm person unity.

Names, filenames, list positions, load order, display labels, and object addresses are not IDs.

One historical person must not become separate Denmark and external-realm people merely because the person appears in several content packages.

---

## 9. External Lock Policy

The four unresolved external locks remain outside Denmark Network ownership.

Each lock requires:

```text
LockId
RequiredExternalOwner
AffectedEdgeIds
MissingOrUnresolvedReference
WhyNetworkCannotResolveIt
PermittedResolutionEvidence
CurrentStatus
MutationBarrier
```

### 9.1 Lock rules

- Denmark Network must not invent the missing external record.
- A lock may block one edge, a subset of edges, or only enrichment fields.
- Unaffected directions may remain admissible if their endpoint and context closure is complete.
- A lock must not silently reduce the expected count of 20.
- Locked directions remain represented in the report as blocked or quarantined, not deleted.
- Resolution requires a versioned update from the external owner or registry.
- A lock closure invalidates older preflight hashes and requires a new dry preflight.

### 9.2 Partial admission

Partial admission is permitted only when:

- the admitted edge has complete canonical endpoints;
- the edge does not depend on an unresolved arrangement;
- its owner and context are unambiguous;
- no blocked edge is synthesized or omitted from reporting;
- the output explicitly identifies admitted, blocked, and quarantined subsets.

## 12. Duplicate and Collision Handling

The validator must separately detect:

- duplicate EdgeId;
- duplicate source-target-context direction;
- same direction repeated with conflicting provenance;
- person/office/title/institution identity collision;
- deprecated and canonical ID both present;
- cross-realm duplicate person;
- reverse direction incorrectly generated from one source direction;
- two external locks claiming ownership of the same unresolved fact inconsistently.

Duplicates must not be silently merged. Merge or replacement requires an explicit deterministic rule and versioned authority.

## 15. Save Contract

Saves preserve:

- canonical edge IDs;
- canonical endpoint IDs and entity kinds;
- context IDs;
- version;
- current network-owned state;
- visibility state;
- relevant source event references;
- unresolved lock or quarantine references when still applicable;
- deterministic processing state required by the owner.

Loading a save must not:

- reapply Denmark Opening State;
- recreate already migrated edges;
- generate missing reverse directions;
- replace evolved runtime values with static defaults;
- resolve locks using a different registry version without migration;
- write deprecated IDs.

Save migration must be idempotent and retain the original save as rollback evidence.

---

## 16. Migration Contract

Legacy or renamed Denmark network references must:

- resolve through direct versioned mappings;
- preserve source provenance;
- reject alias chains;
- preserve edge direction;
- preserve endpoint entity kind;
- preserve context;
- quarantine ambiguous relationship semantics;
- avoid converting kinship or alliance into loyalty or knowledge;
- avoid duplicating reverse directions;
- write only current canonical IDs.

Unknown extension data remains migration evidence or quarantine data and must not enter live network state by proximity.

---

## 17. Determinism Contract

Equal source, contract version, Denmark content version, registry versions, external-owner manifests, Opening State, save state, and seed must produce equal:

- direction count;
- endpoint resolutions;
- context resolutions;
- duplicate findings;
- lock outcomes;
- admitted/blocked/quarantined membership;
- diagnostic codes;
- proposal order;
- normalized output;
- output hash.

Stable ordering uses:

1. NetworkId;
2. SourceNodeId;
3. TargetNodeId;
4. RelationshipContextId;
5. EdgeId.

Processing must not depend on filesystem order, asset discovery order, object address, unordered container iteration, thread completion order, frame timing, wall-clock time, or localized display text.

---

## 18. Performance Contract

The implementation should:

- batch registry resolution;
- resolve each canonical endpoint once per versioned input set;
- use dirty flags and local-neighborhood recalculation;
- avoid full-network per-frame evaluation;
- cache derived summaries only with valid invalidation;
- keep lightweight directions out of routine full AI evaluation;
- produce concise player-facing alerts.

Performance optimization must not weaken ownership validation, lock reporting, provenance, determinism, or save safety.

## 20. Fatal Validation

Reject integration when:

- expected direction count is not 20 and no approved versioned variance exists;
- an edge lacks a stable ID;
- a required endpoint is missing, unknown, ambiguous, deprecated, or wrong-kind;
- a reverse edge was manufactured without authority;
- one mutual score replaces required directional state;
- a person and office, title, dynasty, institution, household, region, or realm share identity;
- Network state grants title, office, claim, knowledge, loyalty, adult agency, or authority automatically;
- static data contains mutable opening or runtime outcomes;
- an external lock is silently ignored;
- a later historical outcome is initialized at opening;
- an advanced save is overwritten by Opening State;
- equal inputs produce unequal normalized results;
- AI or a non-owner directly mutates authoritative state.

---

## 21. Warning Validation

Warn when:

- a direction has no strategic output or clear lightweight purpose;
- an edge context is overly generic;
- a major node lacks expected relationship coverage;
- responsibility or obligation lacks an underlying typed record;
- an edge summary is cached without invalidation;
- network visibility implies knowledge without a valid information path;
- normal turns repeatedly expose low-impact relationship decisions;
- an external lock blocks optional enrichment but is represented as blocking the entire network;
- a relationship label duplicates an office or institutional status.
