## 1. Folder Purpose

This folder is the shared authority and evidence area for named-character identity, portrait presentation, dynamic presentation states, compact and expanded portrait testing, visual-fixture selection, inspection, acceptance, and Phase 7 character-visual sequencing.

The folder keeps five layers distinct:

- **persistent character identity**, defining the recognizable person and appropriate life stage;
- **derived presentation states**, adding bounded office, ceremony, wardrobe, travel, council, command, condition, or contextual treatment;
- **interface tests**, checking readability at practical UI sizes and panel configurations;
- **candidate and inspection evidence**, recording why a visual was accepted, corrected, rejected, retained, or closed;
- **production implementation**, remaining separate until explicitly authorized and validated.

The controlling architectural principle is:

> **Persistent person identity remains stable while office, wardrobe, ceremony, condition, travel, context, and other role-dependent presentation are applied as bounded, removable states.**

Accepted realistic identity masters remain source identities. A later medieval graphic card layer may reinterpret those sources through restrained manuscript, parchment, seal, textile, painted-panel, wood, plaster, metalwork, and appropriate heraldic cues without replacing the underlying person or sacrificing modern campaign readability.

## 7. Asset and Evidence Classes

### 7.1 Identity masters

Identity masters are stable visual sources for named characters. They preserve recognizable identity, appropriate life stage, and character-specific boundaries. They should not permanently bake every office, garment, condition, or scene into the person.

### 7.2 Presentation derivatives

Presentation derivatives adapt an accepted identity for bounded contexts such as compact UI, campaign panels, travel, council, ceremony, office, condition, captivity, mourning, or illness. A derivative does not become a new person and does not supersede the identity master unless a controlling record explicitly says so.

### 7.3 Readability and panel tests

The visible 64-pixel, 128-pixel, 256-pixel, expanded-panel, alignment, frame, grayscale, desaturation, and authority-panel assets are evaluation evidence. They are not individually canonical portraits.

### 7.4 Candidate images

Candidate images preserve selection evidence. A candidate is not authoritative merely because the image remains in the folder. Use the associated review and final acceptance record.

### 7.5 Record types

- **Direction record:** defines the identity or presentation problem before production.
- **Definition and test plan:** states the bounded artifact and acceptance checks.
- **Review:** evaluates a candidate, comparison, or correction.
- **Inspection:** verifies a produced artifact against the stated test.
- **Acceptance:** establishes the accepted asset or set within its boundary.
- **Disposition:** closes or redirects a workstream.
- **Handoff:** passes a mature static result toward another owner without claiming implementation.

## 8. Visual Direction

```yaml
identity_source_layer: RealisticHistoricallyGroundedCharacterMaster
card_art_layer: MedievalGraphicInterpretationAndFraming
information_layer: ClearModernStrategyGameUI
battlefield_layer: ReadableFactionAndRoleIconography
```

The realistic identity source preserves the person. Character, general, agent, and unit cards may later apply a restrained medieval graphic treatment using manuscript, parchment, seal, textile, painted-panel, wood, plaster, metalwork, or appropriate heraldic cues.

This direction does not authorize an exact copy of *Pentiment*, a wholesale conversion of existing assets, generic fantasy panels, or replacement of accepted identities. It preserves the option for a later bounded comparative card-art test after actual first-slice needs are known.

## 9. Naming and Placement Rules

### 9.1 Root placement

Place a file at the `Character/` root only when it controls or compares multiple characters, defines a shared standard or framework, governs Phase 7 sequencing, or consolidates the full character-visual workstream.

### 9.2 Character-folder placement

Place character-specific identity directions, fixture definitions, candidate images, reviews, masters, derived tests, inspections, acceptances, and handoffs inside the matching character folder.

### 9.3 Test-package placement

Keep large derivative-test families inside a clearly named test package beneath the owning character. Do not elevate every test output to the root.

### 9.4 Versioning

Use clean semantic document versions and professional filenames. Create a successor only when substantive content changes. Do not use `FINAL_FINAL`, `NEW`, `REFRESHED`, duplicate-download markers, or similarly ambiguous suffixes.

### 9.5 No symmetry-driven files

Do not create a file, image, folder, or wrapper merely because another character has one. Add an artifact only when a distinct character or systems problem justifies it.

## 10. Working Rules

1. Verify the immediate controlling source before creating a successor.
2. Preserve substantive content through copy-first additive refinement.
3. Keep identity, presentation state, UI treatment, and runtime implementation distinct.
4. Record whether an image is a candidate, accepted master, derivative, study, or test.
5. Inspect compact readability before promoting an image for UI use.
6. Preserve underage scale and distinguish recognized office from adult capacity.
7. Do not infer command, government authority, maturity, or implementation from costume alone.
8. Do not fabricate heraldry, biography, kinship, office, or historical certainty to fill a visual gap.
9. Do not claim Unreal Engine 5.8 validation without implementation evidence.
10. Close a visual cycle once the unresolved systems question has been answered.
