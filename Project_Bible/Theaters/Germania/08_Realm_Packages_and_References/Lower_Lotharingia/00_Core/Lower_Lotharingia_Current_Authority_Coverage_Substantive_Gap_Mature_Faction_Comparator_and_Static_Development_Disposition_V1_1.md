## 1. Purpose and hard boundary

This review answers one question: after the new General Realm Foundation and package navigation work, does the checked Lower Lotharingia portfolio contain a demonstrated non-unit substantive gap that justifies another authority now?

The review is intentionally conservative. It assesses capability coverage, ownership, maturity, unresolved evidence, and development disposition. It does not create units, roster architecture, unit families, candidate units, exact recruitment pools, opening armies, equipment inventories, statistics, regional-unit profiles, mercenary profiles, naval profiles, or Early-to-High military progression. Existing military documents are assessed only as system authorities.

The review also does not initialize people, titles, places, property, armies, agreements, claims, offices, institutional relationships, objectives, or resources. It does not promote preflights, resolve contested evidence by convenience, or convert static design into implementation.

Method:

1. Verify the exact 36-file working set and numbered-folder distribution.
2. Read each body and identify its declared scope, ownership, status, interfaces, unresolved questions, and stop gates.
3. Compare coverage across history, characters, politics, Realm experience, lands, military systems, campaign systems, presentation, and special interfaces.
4. Separate a missing capability from an unresolved fact, a preflight, an implementation matter, or a desirable future refinement.
5. Require a demonstrated player-facing or implementation-helpful capability before recommending a new authority.
6. Keep unit work excluded regardless of military-document references to future roster detail.

This is a content-based static review, not a historical fact-check, live recursive OneDrive inventory, cross-Theater benchmark, source-hash certification of predecessor chains, or Unreal validation.

## 4. Folder-by-folder coverage review

### 4.1 `00_Core`

**Current coverage:** the General Realm Foundation integrates the Realm thesis, contested ducal authority, constitutional separations, strategic identity, ownership map, development channels, continuity, and nonmutation boundaries. The Package Guide indexes the working set but remains navigation rather than substantive authority.

**Disposition:** sufficient. No second foundation, admission authority, identity wrapper, general integration authority, or core manifest is justified now.

**Potential work if triggered:** refine the General Realm Foundation only when a real specialist conflict, accepted primary-source change, or demonstrated cross-system omission is identified. Update the Package Guide when an authority is adopted, renamed, moved, matured, or superseded.

### 4.2 `01_Chars`

**Current coverage:** the portfolio contains Frederick, Ida of Saxony, Adalbero III, the Ardenne-Luxembourg dynasty and ducal household, Godfrey the Bearded, Godfrey the Hunchback, and the Jutta or Judith identity and placement preflight.

**Strength:** the set covers principal leadership, consort and household continuity, dynastic-ecclesiastical intercession, rival restoration politics, conditional succession, and dynasty-level continuity.

**Open issue:** Jutta or Judith remains intentionally unresolved at preflight maturity because identity, age, opening placement, and profile admission require evidence and owner judgment.

**Disposition:** retain the preflight. Do not fabricate a full character profile, invent an opening placement, or create additional relatives merely for family symmetry. No new character authority is mandatory.

### 4.3 `02_History`

**Current coverage:** historical reconciliation, evidence and uncertainty handling, chronology, and historical memory, momentum, emergence, and crisis.

**Strength:** this separates opening admissibility from later history and keeps uncertainty visible rather than converting later outcomes into guaranteed scripts.

## 9. Acceptance tests for future proposed work

A proposed new non-unit file must pass all of these tests:

1. **Capability test:** identify a concrete player-facing or implementation-helpful question that no current owner can answer.
2. **Owner test:** show why adding to the nearest existing authority would create an ownership defect or unmanageable scope.
3. **Evidence test:** distinguish verified evidence, project design, uncertainty, and exact-state deferral.
4. **Nonduplication test:** demonstrate that the proposal is not a renamed wrapper or symmetry file.
5. **Boundary test:** preserve unit hold, Opening State hold, registry hold, and Unreal hold.
6. **Copy-first test:** if a substantive predecessor exists, read and preserve it before creating a successor.
7. **Stop test:** if the above tests fail, create nothing.

A proposed refinement to an existing file must preserve useful sections, tables, portfolios, ownership boundaries, uncertainty treatment, validation boundaries, and the three progression tracks. Any substantive removal requires an explicit ledger.
