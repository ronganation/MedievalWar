## 1. Purpose

This README is the primary landing page for the Barcelona `Units_Roster` folder. It records the verified physical structure, routes readers to the current Early and independent High portfolios, separates research and reconciliation material from unit profiles, identifies development and progression authorities, and prevents obsolete or supporting files from being treated as interchangeable with current portfolio owners.

This README is an organizational and currentness guide. It does not independently create a unit, promote a proposal, assign a canonical identifier, establish an opening army, activate a recruitment pool, finalize numerical balance, generate payloads, or authorize Unreal mutation.

## 9. Currentness and predecessor rules

- Preserve Early profiles as the Early layer. A High successor does not erase the Early unit or its historical role.
- Prefer the most mature verified profile within the correct era and branch when several files describe related concepts.
- Treat filenames containing `Research`, `Evidence`, `Decision`, `Gate`, `Reconciliation`, `Acceptance`, or `Matrix` as supporting or governing records according to their contents, not as unit profiles by default.
- Treat `Development_Progression` files as relationship authorities, not replacement Master Unit Profiles.
- Do not infer that every Early profile must have a one-to-one High successor.
- Do not create symmetry-only units to fill a branch.
- Do not collapse Barcelona's independent High portfolio into Barcelona-Aragon. The emergent union may inherit, retain, transform, combine, or decline elements through its own authorities.
- Do not duplicate Theater-owned regional or mercenary profiles inside this folder.
- Do not mark a file Active merely because it is current within the static design portfolio.

## 10. Development-path interpretation

The portfolio supports continuity and development across three broad branches:

1. Infantry and household foot.
2. Foot archers, crossbowmen, and skirmishers.
3. Cavalry and mounted household forces.

These paths are connective design structures, not automatic upgrade buttons. Progression must preserve recruitment source, social basis, equipment availability, regional identity, battlefield role, roster survival, and replacement-versus-coexistence decisions documented by the appropriate progression authority and profile pair.

## 11. Barcelona identity boundary

The folder should express independent Barcelona through:

- comital and county institutions rather than generic royal framing;
- regional and civic recruitment without erasing local origins;
- a mixed military base of levy, castellany, household, urban, ranged, skirmish, and mounted forces;
- explicit Early-to-High development rather than a flat era-free list;
- selective access to external, regional, mercenary, military-order, and Aragon-linked capabilities without transferring ownership;
- survival of distinctive Early identities where later development does not justify replacement.

This section is routing guidance for maintaining coherence. Individual unit files remain the source for exact unit identity and battlefield specification.

## 12. File-placement rules

Place files as follows:

- Evidence, source reviews, admission research, collision analysis, and reconciliation records: `00_Research_Evidence_Review`.
- Early unit profiles: the correct branch under `01_Early`.
- Independent High unit profiles: the correct branch under `02_High/01_Independent`.
- Branch-wide relationship and progression authorities: that branch's `Development_Progression` folder.
- Whole-portfolio closeout or map authority: the `Units_Roster` root when it genuinely governs all branches.
- README and current portfolio index: the `Units_Roster` root.

Do not move source files merely to make naming uniform. Any reorganization should use an exact move map, preserve donor files until verified, and finish with recursive validation.

## 13. Known hygiene issues and bounded corrections

### 12.1 Folder spelling

`02_High/01_Independent/03_Calvary` is a physical folder-name defect. The intended military category is cavalry. This README records the defect but does not rename the folder.

### 12.2 Royal versus comital naming

`01_Early/05_Royal_Household` contains comital profiles. The mismatch should be reviewed before any rename. No political-rank change is authorized by this README.

### 12.3 Mixed naming conventions

The portfolio contains files with and without the `Barcelona_` prefix and files using `_FULL`, correction, refinement, or closeout suffixes. Currentness must therefore be determined from source relationships and portfolio authorities, not filename aesthetics alone.

## 14. Completion and stop gate

The verified folder has a substantial Early portfolio, developed independent High infantry, missile, and cavalry branches, branch-level progression material, a research and reconciliation record, and a root portfolio closeout map.

The correct next state is maintenance and targeted refinement, not indiscriminate file creation. A new unit or authority is justified only when review demonstrates a substantive battlefield, progression, recruitment, historical, or player-facing gap that the current portfolio does not already cover.

No Late-era folder should be created merely for symmetry. No Barcelona-Aragon union folder should be inserted into this independent Barcelona portfolio without a separate ownership and inheritance decision.

## 16. Maintenance checklist

When the folder changes:

1. Recursively inventory the affected branch.
2. Identify the immediate substantive source and any successor relationship.
3. Verify that a candidate is evidence, profile, progression authority, reconciliation record, or closeout authority.
4. Update the relevant inventory section without deleting useful predecessor history.
5. Check Barcelona-versus-Aragon-versus-union ownership.
6. Check Regional Unit and Mercenary Unit canonical ownership at Theater level.
7. Check Early and High coexistence or replacement semantics.
8. Check naming, path length, exact folder placement, and links.
9. Keep opening state, registry, payload, importer, and runtime status nonactive unless separately authorized.
10. Stop when no substantive gap remains.
